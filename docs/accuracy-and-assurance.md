# Accuracy and assurance model

This scanner provides **offline, regex-led triage**. It helps a reviewer find code worth
investigating; it does not prove that a vulnerability is exploitable or that an unreported issue
does not exist.

## What the result means

Each finding combines four separate concepts:

- **Rule ID** identifies the detector and is the stable reference for review and suppression.
- **Severity** is the potential impact used to prioritize triage. It is not a CVSS score.
- **Confidence** estimates how characteristic the matched syntax is. It is not a probability.
- **Location and context** point the reviewer to evidence; retained reports redact credential
  source lines by default.

Confirmation still requires language-aware review of input control, data flow, reachability,
sanitization, permissions, and runtime behavior. A clean report means only that no enabled rule
matched the scanned, readable, in-scope files.

## Evidence levels

| Level | Evidence | Supported conclusion |
|---|---|---|
| Pattern smoke test | Small built-in synthetic examples | Core pattern machinery starts and selected rules can match |
| Rule corpus | Named positive and negative fixtures with exact expected rule IDs | Current behavior on the committed cases |
| Regression tests | Output, redaction, traversal, error, and CLI contracts | Tested contracts hold on the CI matrix |
| External benchmark | A versioned third-party corpus with a documented mapping | Comparative accuracy on that selected dataset only |
| Manual/dynamic validation | Application-specific review or execution | Whether a particular candidate is reachable or exploitable |

Run the committed corpus evaluation with:

```bash
python scripts/evaluate_corpus.py
```

The evaluator reports exact expected-versus-observed results. It should fail when a rule change
introduces a missed expected finding or an unexpected finding. Corpus cases are synthetic and are
not a claim of broad language coverage. New rules should include at least one realistic positive,
one near-miss negative, and an explicit language/file-kind boundary.

## Accuracy reporting

When publishing benchmark results, record all of the following together:

1. scanner commit and configuration;
2. corpus name, version, licence, and exact included subset;
3. expected-label mapping and any excluded/unsupported cases;
4. true positives, false positives, false negatives, and true negatives by rule and language;
5. precision and recall with raw counts, plus scan errors and resource-limit truncation;
6. whether results were generated by pattern matching, syntax-aware validation, or manual review.

Do not compare an internal rule corpus directly with a full SAST benchmark: a curated corpus is a
regression oracle, while an external benchmark tests a wider and less controlled population.

## Sources of false positives

- comments, documentation, generated code, fixtures, and deliberately vulnerable training code;
- APIs used safely because a nearby control or fixed input is outside the matched text;
- weak algorithms used for non-security checksums or compatibility rather than protection;
- framework-safe wrappers that resemble a lower-level unsafe sink.

Use includes/excludes, confidence filters, or a rule-scoped Python suppression only after review.
Suppressions are evidence to audit, not proof that a match is safe. Prefer
`# nosec: RULE.ID -- concise justification`; use `--require-suppression-reason` and
`--fail-on-suppressed` when an authoritative gate must enforce exception policy.

## Sources of false negatives

- aliases, wrappers, reflection, metaprogramming, split strings, and multi-file data flow;
- unsupported syntax, encodings, file types, frameworks, and secret formats;
- sanitization or sink behavior that requires semantic or runtime reasoning;
- unreadable, excluded, oversized, binary, linked, or resource-limit-truncated inputs.

Operational errors make the default command exit `2`; do not use `--best-effort` for an
authoritative gate. Use another language-aware SAST tool, dependency scanner, secret scanner, and
manual review where the application risk warrants them.

## JSON contract

v2.2 JSON reports carry a top-level `schema_version`. Consumers should reject unknown major
schema versions and validate reports against
[`schemas/vulnscan-2.2.schema.json`](../schemas/vulnscan-2.2.schema.json). The scanner's product
version and report schema version are separate: a compatible product update does not necessarily
change the schema. `summary.complete` must be true before a report is interpreted as clean;
`summary.truncated` identifies resource-bound partial results, while `suppressions` retains
redacted accepted findings for audit.
